## Core design

The SQLite journal in 'storage/import_journal.py' is durable on disk. It uses
'BEGIN IMMEDIATE' transactions, unique paper keys, and per-job leases. A job is
uniquely identified by (parent page ID, resource type, arXiv ID). The payload
hash binds it to a specific rendered Notion block tree.

The remote page title carries the stable marker '⟦A2N:...⟧'. This is visible
to users on purpose: Notion does not provide a client-specified idempotency key
for pages.create, and a title marker allows recovery when its HTTP response
is lost. The connector must have access to list the root page's children.

Every batch follows this sequence:

1. Persist the batch payload fingerprint as 'in_flight'.
2. Send the create/append request with no blind retries for ambiguous errors.
3. Paginate through Notion's children and compare a projected representation
   of every existing block against the intended ordered prefix. For nested
   table/toggle content, recursively fetch children.
4. Record confirmed batch and total prefix length ONLY after read-back matches.
5. If the response is lost but remote content matches, mark the batch confirmed
   and continue; if unconfirmed, stop with 'uncertain'.
6. On resume, inspect the remote page before deciding which batch (if any)
   can safely be appended. A changed payload or manual edit is a conflict,
   never silently overwritten.

Reference pages use the same checkpoint/reconciliation mechanism, with their
parent set to the verified main page.

## Operational usage

    NOTION_SYNC_ENABLED=true
    IMPORT_STATE_DB=./data/imports.sqlite3
    python main.py 1706.03762

The state database MUST be stored on persistent writable storage (not a
stateless container's ephemeral layer). Back it up together with artifacts.

To resume, repeat the same import with identical conversion, metadata, model
annotations and import options. Do NOT clear the cache or delete the SQLite
database to 'fix' an uncertain job. The job's identity is bound to its payload.

When a pending append could not be observed remotely after a timeout, the
default is fail-closed. Only after independent verification that the request
did not apply may the operator opt into:

    python main.py 1706.03762 --retry-uncertain

The opt-in cannot guarantee exactly-once effects under eventual consistency.
For a lost page-create response with no discoverable marker, even explicit
retry will NOT create another page: manual investigation is required.

## Limits

* A manually renamed page that loses its marker cannot be rediscovered unless
  its page ID is already persisted.
* The Notion API can normalize block payloads. Unsupported/changed block types
  fail closed rather than creating a false completion.
* The read-back compares the expected original content prefix, excluding
  reference child pages. It is not a cryptographic server-side commit receipt.
* This release does NOT implement automatic editing of existing paper versions,
  distributed leases over multiple machines, or a PDF gold-corpus benchmark.
* Importing the same arXiv identity with changed annotations/metadata requires
  an explicit future update/migration workflow.
* The synchronous Notion client still blocks the coordinator's event loop.

The new tests inject lost responses, duplicate submissions, remote mutation,
large paginated pages, nested blocks, conflicting batches, and concurrent
claims. No live Notion credentials are used in CI.

## Additional correctness details

The SQLite journal uses WAL with full synchronous durability and disallows
concurrent leases on one logical import. Duplicate citations to the same
arXiv reference resolve to one child page and one accounting entry.

## SDK retry policy and legacy imports

The durable writer disables the Notion Python SDK's own automatic retries so
that non-idempotent write attempts are controlled by the SQLite journal. It
performs retry-after-aware retries for explicit 429 responses and safe reads.
Other ambiguous write errors always require remote verification first.

Previously imported pages that predate M02 do not have identity markers.
The first M02 import may create a separate page rather than modify an old,
unmarked page. Inspect and migrate such pages manually before enabling durable
sync for existing Notion libraries; automatic adoption by matching a title is
not safe.

**Legacy duplicate guard:** a new durable import refuses to create a page
when an unmarked child page has the same visible title. This is not a generic
migration: renamed pages and different display titles require manual audit.
